把协作写清楚，让交付有据可查。

一个把任务、依赖与验收写清楚的本地协作实践：公开版负责把计划写明白，本地版在既有环境里按队列执行。

问题

同时使用多个 AI 工具时，任务与交付之间的边界容易失去联系：一个任务交给了谁、依赖哪一步的产物、验收标准是什么，往往只存在于对话记录里，事后难以核对。

这个项目尝试用一份写得清楚的协作计划来解决：任务有定义，依赖有顺序，验收有记录。角色分工如下——

“我负责需求定义、流程设计与结果验收；AI 工具参与实现，问题通过实际产物和独立检查发现与修正。”

流程示意

三个步骤依次相连：每一步的产物是下一步的输入。

  1. 01

    明确任务

    把需求写成任务单：目标、边界、依赖关系与验收标准，在动手之前先写清楚。

  3. 02

    执行任务

    按队列与依赖顺序执行，产出可核对的实际产物，并记录产物哈希用于验收。

  5. 03

    检查验收

    对照任务单验收：独立测试、复核记录与产物哈希，留下有日期的证据。

公开版与本地版

公开版与本地版能力比较
能力 公开版（本页工具） 本地版
任务文本 生成结构化的任务说明文本 读取同一份任务定义
依赖预览 可视化任务之间的依赖顺序 按依赖顺序调度执行
JSON 导出 导出完整计划 JSON，供审阅与复用 消费该 JSON 作为执行输入
模型请求 不请求任何模型，纯本地生成 利用既有环境与会员路由执行队列
凭证与隐私 不接触任何凭证 个人会员凭证、私人任务和控制接口留在本地，不进入公开页面

本地使用说明

  1. 先用公开版生成计划，审阅导出的 JSON，确认任务、依赖与验收标准符合预期。
  2. 再把 JSON 交给你自己的本地执行环境。本地版需要你自己的执行器与凭证，本页不提供。
  3. 没有执行环境时，也可以把计划当作 Markdown 任务单，交给任意 AI 工具逐条执行。

本页不安装、不连接、不执行任何东西。公开版只在你的浏览器里生成文本与 JSON。

边界与已知限制

  • 每个任务总共最多 2 次尝试——是“总共 2 次尝试”，不是“2 次重试”。失败后不会无期限自动重试。
  • 模型复核不等于事实证明；复核意见需要与实际产物和独立检查相互印证。
  • 自动检查只覆盖指定验收约定中写明的范围，约定之外的行为不作保证。
  • Claude Code 接入 Kimi 已通过基础代码小样；Desktop 界面和长任务尚未全面验证。
